## Запуск автотестов

Нужен Docker с Docker Compose v2. Python и браузеры ставить не нужно.

```bash
docker compose run --build --rm tests
```

Ожидаемый результат:

```
tests/test_booking.py ..xxx
tests/test_smoke.py .
======================== 3 passed, 3 xfailed ========================
```

- `x` (xfailed) — тест известного дефекта BUG-01 упал на проверке ожидаемого поведения, как и должно быть, пока дефект не исправлен. Если дефект исправят, тест станет `XPASS(strict)` и прогон упадёт: это сигнал снять маркер `xfail`.
- Результаты — в `artifacts/`: `junit.xml` (в JUnit xfail-кейсы записываются как `skipped type="pytest.xfail"` — стандартное поведение pytest) и `browser/` со скриншотами и trace при падении.
- Другой адрес стенда: `BASE_URL=https://… docker compose run --build --rm tests` или `--base-url`.
- Один тест: `docker compose run --build --rm tests python -m pytest tests/test_booking.py -k successful`.
- Без Docker:

  ```bash
  python -m pip install -r requirements.txt
  python -m playwright install chromium
  python -m pytest
  ```

- CI: [.github/workflows/tests.yml](.github/workflows/tests.yml) запускает ту же команду на каждый push и PR и сохраняет `artifacts/`.

## Дефекты

Все дефекты воспроизведены на опубликованной странице в Chromium 156, окружение — [выше](#окружение). Общие условия: страница открыта заново, остальные поля заполнены корректно: «Средняя», завтра, 10:00–11:00, 6 участников, «Иван Петров», `ivan@company.ru`.

### BUG-01. Не проверяется длительность брони (30 минут – 4 часа)

- **Приоритет:** высокий. Нарушено явное бизнес-правило: можно создать бронь нулевой длины или занять комнату на весь день и заблокировать её для остальных.
- **Шаги:** 1) Начало 10:00, окончание 10:00. 2) «Забронировать». 3) Повторить для 10:00–10:10, 10:00–10:29, 09:00–13:01, 09:00–18:00.
- **Ожидаемый результат:** бронь не создаётся, показана ошибка о допустимой длительности от 30 минут до 4 часов.
- **Фактический результат:** во всех случаях «Бронирование создано», например «Средняя, 2026-11-26, 10:00–10:00 · Иван Петров». Границы 30 мин и 4 ч принимаются, как и должны.
- **Причина (по коду):** `script.js:40` проверяет только `endTime < startTime`, проверки длительности нет. Поэтому и начало, равное окончанию, проходит.
- **Доказательство:** [0 минут](docs/evidence/bug-01-duration-0min.png), [9 часов](docs/evidence/bug-01-duration-9h.png).
- **Автотест:** `test_discovered_defect`, кейсы 10:00–10:00, 10:00–10:10, 09:00–14:00. Это подмножество шагов выше: по одному кейсу на «ноль», «меньше 30 минут» и «больше 4 часов».

### BUG-02. На сегодня можно забронировать уже прошедшее время

- **Приоритет:** высокий. Нарушено явное требование, бронь «в прошлое» бессмысленна и искажает загрузку комнат.
- **Условия:** текущее время позже 01:00 по часовому поясу браузера.
- **Шаги:** 1) Дата — сегодня. 2) Начало 00:00, окончание 01:00 (подходит любой интервал раньше текущего времени). 3) «Забронировать».
- **Ожидаемый результат:** ошибка «нельзя выбрать прошедшее время», бронь не создаётся.
- **Фактический результат:** бронь создаётся. На скриншоте прогон в 21:03 UTC с интервалом 08:00–09:00: «Бронирование создано. Средняя, 2026-11-25, 08:00–09:00 · Иван Петров». Время прогона — в [exploratory-run.json](docs/evidence/exploratory-run.json) (кейс `date_today_past`) и в журнале команд, сам скриншот часов не показывает.
- **Причина (по коду):** `script.js:38` сравнивает только дату, время начала с текущим не сравнивается.
- **Доказательство:** [скриншот](docs/evidence/bug-02-past-time-today.png).
- **Почему нет автотеста:** результат зависит от времени запуска: около полуночи прошедшего времени нет. Для стабильного теста нужно фиксировать время браузера через `page.clock` — предлагаю следующим шагом.

### BUG-03. HTML и JavaScript из поля «Имя» выполняются на странице

- **Приоритет:** высокий. Это XSS. Сейчас он срабатывает только у того, кто ввёл данные (self-XSS, ничего не сохраняется), но как только имя начнут сохранять и показывать другим (список броней, уведомления), это станет хранимым XSS. Исправление дешёвое: `textContent` вместо `innerHTML`.
- **Шаги:** 1) В «Ваше имя» ввести
  `<b>Иван</b><img src=x onerror="document.title='XSS выполнен'; this.insertAdjacentHTML('afterend','<mark>&nbsp;JS из поля «Имя» выполнен&nbsp;</mark>')">`
  2) «Забронировать».
- **Ожидаемый результат:** в сообщении имя показано как обычный текст, теги видны буквально.
- **Фактический результат:** «Иван» выводится жирным, скрипт из `onerror` выполняется: заголовок вкладки меняется на «XSS выполнен», после имени появляется вставленный скриптом жёлтый текст «JS из поля «Имя» выполнен».
- **Причина (по коду):** `script.js:78` — `status.innerHTML` со значением `data.name`.
- **Доказательство:** [скриншот](docs/evidence/bug-03-xss-name.png).

### BUG-04. Принимается дробное количество участников

- **Приоритет:** средний. Число людей не бывает дробным, в данные брони попадает некорректное значение. Пользователь не видит проблемы: число участников в сообщении не выводится. Другие правила для этого поля работают.
- **Шаги:** 1) «Участники» — `2.5`. 2) «Забронировать».
- **Ожидаемый результат:** ошибка «укажите целое число от 1 до 20».
- **Фактический результат:** «Бронирование создано».
- **Причина (по коду):** у формы стоит `novalidate` (`index.html:47`), поэтому встроенная проверка браузера (`min`, `max` и шаг 1 у `type=number`) отключена. Скриптовая проверка `script.js:44-50` смотрит только диапазон, а не то, что число целое. Добавить `step="1"` недостаточно: проверка нужна в `validate()`.
- **Доказательство:** [скриншот](docs/evidence/bug-04-fractional-participants.png).

### BUG-05. Принимаются некорректные адреса почты

- **Приоритет:** средний. Нарушено явное требование «электронная почта имеет корректный формат», во всех браузерах. Заявитель с опечаткой в адресе не получит подтверждение и не узнает об этом. Самые грубые ошибки (без `@`, без домена верхнего уровня, только пробелы) форма ловит, поэтому приоритет не высокий.
- **Шаги:** 1) В «Рабочая почта» ввести `test@@mail.ru`. 2) «Забронировать». 3) Повторить для `a@b..ru` и `ivan,petrov@mail.ru`.
- **Ожидаемый результат:** ошибка «Введите корректную рабочую почту», бронь не создаётся.
- **Фактический результат:** во всех трёх случаях «Бронирование создано». Для сравнения: `a@b` и `"   "` форма отклоняет правильно.
- **Причина (по коду):** `script.js:52` — регулярное выражение `^\S+@\S+\.\S+$` пропускает любые непробельные символы, включая второй `@`, запятую и две точки подряд.
- **Доказательство:** [скриншот для `test@@mail.ru`](docs/evidence/bug-05-email-invalid-format.png).

## Автотесты

Файл [tests/test_booking.py](tests/test_booking.py). Smoke-тест каркаса в эти три не входит.

| Тест | Что проверяет | Что его уронит |
|---|---|---|
| `test_successful_booking` | «Средняя», завтра, 10:00–11:00, 6 участников → статус `success`, в сообщении «Бронирование создано», комната, дата, время, имя; ни одно поле не подсвечено ошибкой | бронь не создаётся, в сообщении нет или неверны комната/дата/время/имя |
| `test_invalid_booking` | «Малая» + 5 участников → статус-ошибка, сообщения об успехе нет, у «Участники» ошибка с «максимум 4» | пропала или сломалась проверка вместимости |
| `test_discovered_defect[zero-minutes / 10-minutes / 5-hours]` | бронь вне диапазона 30 мин – 4 ч не создаётся (нет «Бронирование создано»). `xfail(strict=True, reason="BUG-01: …", raises=AssertionError)` | исправление BUG-01 → `XPASS(strict)`, то есть сигнал снять маркер |

Решения:
- **Локаторы по тому, что видит пользователь:** `get_by_label`, `get_by_role`. Они переживают редизайн вёрстки, если подписи полей не меняются. CSS-селектор используется только для текста ошибки поля: у него нет роли и связи с полем (О-4).
- **Один хелпер `fill_booking_form(**overrides)`** и словарь `VALID_BOOKING`: каждый тест меняет только то, что проверяет. Хелпер содержит только действия без проверок. Поэтому сбой окружения (страница не открылась, поле не найдено) даёт `Error`/`TimeoutError` и честное падение, а не ложный xfail.
- **Дата берётся у страницы** (`min` поля даты + 1 день), а не из `date.today()`. Тесты не зависят от часового пояса контейнера и времени запуска.
- **Тест дефекта проверяет результат, а не место ошибки.** Требования не говорят, у какого поля должна быть ошибка длительности, поэтому тест проверяет только, что бронь не создана. Исправление с ошибкой у любого поля будет замечено.

Как проверялись сами тесты (временные копии приложения в `artifacts/`, после проверки удалены, приложение в репозитории не менялось):
- копия с добавленной проверкой длительности, `--runxfail` → 5 passed: тест дефекта проверяет корректное поведение и при исправлении проходит;
- та же копия в обычном режиме → 3 × `XPASS(strict)`, прогон красный: исправление не останется незамеченным;
- копия без проверки вместимости → `test_invalid_booking` падает на `AssertionError`;
- копия без имени в сообщении → `test_successful_booking` падает на `AssertionError`.

## Вопросы и допущения

Вопросы к аналитику:
1. «Рабочая почта» — только корпоративный домен? Допустимы ли кириллические домены (`почта.рф`)? Сейчас принимается любой адрес. Допущение: проверяем только формат.
